# RWTH SEM superresolution audit

**19 November 2026.** Use the full 16MnCrS5 frames, retain only a small, capped contribution from native DP-small images, and leave `DP/100mu` out of the first ViT-L run. At audit time, the 191,400 HR PNGs made up 55.5% of the candidate manifest by file count. That weight substantially overrepresented two steel specimens and, in the case of 16MnCrS5, the same fields of view. The later user-selected V0 subset is documented separately. [V0 selection](rwth_sem_posttraining_v0_selection.md)

## Tiles, overlap and ordering

- **16MnCrS5.** For each large HR/LR pair, the generator lays out 128×128 HR and 32×32 LR tiles with nominal strides of 96 and 24 pixels, respectively. The nominal overlaps are 32 and 8 pixels, or 25% per axis. `overlap=0.75` in the code is the fraction used for the step. A 16-pixel HR search margin allows local alignment against the separately recorded LR image. The code searches over decimated HR candidates using negative MSE, fits a linear drift correction, rounds coordinates, then directly slices the HR raster. No geometrical resampling of the actual exported HR tile is needed. The geometry gives `((3072 − 32) // 96 − 1)² = 30²` tiles per source. With numeric ID `n`, `n//900` identifies the likely source block, `(n%900)//30` the row and `n%30` the column. The original per-block filename order comes from an unsorted filesystem glob and was not saved. Actual HR origins can deviate from the nominal grid by drift. In a bounded check, 80 of 81 consecutive pairs shared an identical 32-pixel horizontal strip, with the remaining pair at a row boundary. All 81 pairs separated by 30 IDs shared exact pixels at displacements `(96,0)` (78), `(95,0)` (2) or `(96,1)` (1), in row/column order. Archive code under `code/sr_dataset_generation/`, `src/scripts/process_larger_micrographs.py` lines 43–56 and 77–114, `src/alignment/linear_drift.py` lines 57–93, `src/alignment/search_and_find.py` lines 22–39, `src/pre_processing/divide_micrograph.py` lines 24–27. [Pair evidence](../outputs/dataset_audits/rwth_sem_sr_2026-11-19/adjacency_evidence.json)
- **DP/10mu.** Its 128×128 HR and 32×32 LR dimensions match the native small capture windows in the paper. A shared ID associates the two scans of a field and an assigned reference. A raster grid or stride does not follow from those IDs. Pixel checks found no exact overlap in 45 sampled consecutive HR pairs. This does not test whether different recorded fields physically overlap. [Paper §2.2 and Table 1](https://publications.rwth-aachen.de/record/1012191/files/1012191.pdf#page=3) · [Pair evidence](../outputs/dataset_audits/rwth_sem_sr_2026-11-19/adjacency_evidence.json)
- **DP/100mu.** The paper's §3.1.1 describes stitching overlapping **predictions** with the middle 62.5% retained. The shipped `legacy/prepare_large_micrographs/prepare_DP.ipynb`, JSON lines 150–182, shows a demonstration using a stride of 80 HR pixels and 48 pixels of overlap. It converts the source TIFF values to 8-bit and takes direct crops. Its loop gives 50×50 positions for a 4096×4096 frame and saves into `data.h5` in a later cell (lines 210–216). Neither that output nor its counts establish how the 22,119 released PNGs were generated. The first ID failed the overlap check against offsets including 40–42 and 49–50. None of 45 sampled consecutive HR pairs matched an exact translated overlap. The branch's true stride, acquisition count and tile-to-source coordinates remain unresolved. [Paper §3.1.1](https://publications.rwth-aachen.de/record/1012191/files/1012191.pdf#page=6) · [Pair evidence](../outputs/dataset_audits/rwth_sem_sr_2026-11-19/adjacency_evidence.json)

I also indexed the edge strips of 1,024 randomly selected DP/100mu HR tiles without relying on their ordering. There were zero exact horizontal or vertical matches at strides of 80, 96 or 102 pixels. The same check recovered all 60 expected adjacencies in the 36-tile 16MnCrS5 control at stride 96. The test covers unshifted, pixel-identical strips on the sampled layouts. Drift, other strides or a different export could still produce overlap. [Stride probe](../outputs/dataset_audits/rwth_sem_sr_2026-11-19/stride_probe.json)

**Augmentation.** The matched 16MnCrS5 generator exports crops and copies the grayscale channel into RGB. The shipped training loader applies flips and quarter-turns after reading images, in `code/ttsr/dataset/cufed.py`, lines 21–48, 76–80 and 150–152. An evenly spaced 128-image HR sample per group had no exact rotation or reflection matches within each sample. This supports the absence of a systematic saved rotation set. The unmatched `DP/100mu` export recipe remains unknown. [Archive evidence](../outputs/dataset_audits/rwth_sem_sr_2026-11-19/archive_evidence.json)

## Native frames and recovery

- The only full-size TIFs in the open ZIP are `data/16MnCrS5/show/SE_7.tif` and `SE_19.tif`, each 3072×3072 and grayscale. The code copies these from the source directory before tiling. Pixel matches locate their HR blocks at IDs **130500–131399** and **78300–79199**, respectively. A nominal 30×30 HR grid covers about 2912×2912. Its shifted tile coordinates leave unobserved margins in the 3072×3072 raster, so ordinary HR blocks cannot recover the full frame. An interior mosaic needs verified integer offsets and equal overlap values. Using nominal positions everywhere would ignore measured drift.
- **The 16MnCrS5 reference stack preserves three more full-frame pixel grids.** The generator traverses `SE_0`, `SE_22`, `SE_144` in that order and saves a 24×24 grid of non-overlapping 128×128 tiles per source (lines 14–34, 43–45 and 63–80 of `process_larger_micrographs.py`). The corresponding 576-tile groups begin at reference IDs 0, 576 and 1152, and link by exact pixel overlaps to HR block starts 50400, 112500 and 109800. Sampled correspondences farther into each grid also match. The stored grayscale rasters can be reassembled by placing the published pixels in row-major order, subject to confirming tile coverage and shape at export. Independent full-frame comparison and original TIFF container metadata are unavailable for those three. [Reference mapping evidence](../outputs/dataset_audits/rwth_sem_sr_2026-11-19/reference_mapping.json)
- **Assigned references do not locate the HR tiles.** The selector chooses texture matches for each LR entry and saves the chosen reference under its ID (`src/pre_processing/assign_reference_imgs.py`, lines 12–25). In 16MnCrS5, 144,000 assigned reference files reduce to 1,728 ZIP CRC/length keys, all present in its stack. DP/10mu ships 225 separate 300×300 reference files and uses 194 distinct reference CRC/length keys. DP/100mu has 90 distinct assigned-reference keys and no separate stack. The DP reference assignments provide no coordinates. The 4096×4096 DP TIFF and the remaining 16MnCrS5 TIFFs were absent from the open ZIP. The paper directs readers to this record. A related restricted Zenodo record describes the triplets and code but supplies no public raw-frame inventory. No separate public raw-frame source was found. Ask the authors for the raw HR frames and the exact crop-to-acquisition table if more coverage is needed. [Paper data and code availability](https://publications.rwth-aachen.de/record/1012191/files/1012191.pdf#page=10) · [Related restricted record](https://zenodo.org/records/15231958) · [Archive evidence](../outputs/dataset_audits/rwth_sem_sr_2026-11-19/archive_evidence.json)

**Demonstration.** I joined 36 tiles from the verified SE_7 block on the 96-pixel grid to produce a 608×608 crop at original row 19, column 18 (zero-based). Every shared pixel agreed and the result differed from the TIFF crop at **0 of 369,664 pixels**, with no gaps. This is an exact reconstruction of the covered region. The full TIFF is already available in the archive. ## Recommendation for ViT-L/14 at 518 / 224

Upscaling 128×128 to 518×518 enlarges it about 4.05× per side. A 224×224 local view still requires 1.75× scaling even if it uses the entire tile. These views can teach fine-scale texture and morphology, but they contain far less spatial context than crops taken from full scans, and smaller random crops amplify the problem.

| Group | Recommendation | Sampling rule |
| --- | --- | --- |
| **16MnCrS5** | **Use full-resolution frames.** Start with the two archived TIFFs and prefer obtaining the remaining originals. The three reference grids are a viable fallback. | Sample by acquisition first, then choose crops. Count a reconstructed frame and its overlapping HR tiles as one source. Keep the two steel samples' contribution bounded within the wider SEM mixture. |
| **DP/10mu** | **Keep the native 128×128 HR tiles with a cap.** They add real small-window DP fields. | As an initial setting, cap them at around 1% of total draws, use one HR member per pair, and use the full source tile as the available field when resizing. If stage/acquisition-area metadata becomes available, distribute draws across areas. |
| **DP/100mu** | **Exclude from the first run.** The local folder cannot be mapped reliably to the paper's original or put on a verified grid. | If the raw frame or an acquisition map becomes available, review the overlap and sample by verified acquisition, with one source unit if the paper's single frame is confirmed. |

Acquisition-level selection matters more here than removing exact duplicate files. Uniform file sampling would turn each 16MnCrS5 scan into roughly 900 opportunities to be drawn and would assign the uncertain DP/100mu folder the weight of 22,119 separate fields. No dataset or manifest edits were made. Checks used ZIP headers, the included source code and bounded pixel comparisons. The audit involved no large downloads or training.
